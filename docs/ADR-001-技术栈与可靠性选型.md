## 1. 上下文与问题陈述 (Context & Problem)

公司在 SAP Business One 10.0 (SQL Server 2022) 环境下，通过无源码的第三方辅助平台开发了“型号订单 `CHORDR`”、“型号报价单 `CHOQUT`”等业务单据。现需建设一套通用的企业级审批平台，面临以下核心诉求与边界：
1. **通用性与可配置**：服务于多个 UDO，具备条件分支、串并行、会签/或签、加签、退回及版本化流程管理能力。
2. **黑盒集成**：第三方辅助平台无源码，仅可复用其“动态赋予 Web 浏览器 URL”与“表格黄箭头穿透”能力，网页无法直接调用 SAP UI API。
3. **高可靠性与强一致性**：审批过程不能依赖跨系统分布式大事务，必须具备快照防篡改 (SHA-256)、网络中断重试、服务崩溃自愈、重复点击幂等性防护。

---

## 2. 决策方案 (Decisions)

### 2.1 后端技术栈：.NET 8 (C# 12) + DDD 整洁架构
- **核心选型**：ASP.NET Core Web API 8.0。
- **分层拓扑**：
  - `Approval.Domain`：纯领域核心（零外部依赖），封装流程状态机、聚合根（`WorkflowInstance`、`WorkflowTask`、`Snapshot`）、领域事件与不可变快照计算。
  - `Approval.Application`：CQRS 用例、命令/查询处理器、适配器契约与 DTO 转换。
  - `Approval.Infrastructure`：EF Core 8 / Dapper、SQL Server 2022、Outbox 消息持久化、行版本乐观并发控制、TraceID 追踪。
  - `Approval.SapAdapter`：Service Layer REST 交互客户端、UDO 模式识别与规范化 JSON 序列化器。
  - `Approval.Api`：RESTful 控制器、Swagger OpenAPI 文档、全局异常/鉴权中间件。
  - `Approval.Worker`：Outbox 消息分发中继、超时自动升级、补偿重试守护进程。
- **跨平台与跨架构支持**：原生编译支持 Windows x64 与 ARM64 架构。

### 2.2 前端技术栈：Vue 3 + TypeScript + Vite + Pinia
- 采用现代响应式架构与 CSS 变量设计系统，高分屏 (High-DPI) 与低分屏自适应。
- 零外部重量级 UI 框架侵入，轻量纯净，在 SAP 客户端内嵌浏览器控件中具备极速渲染与低内存占用优势。

### 2.3 数据一致性：Outbox 模式 + 幂等状态机 (Idempotent Consumer)
- 放弃易造成死锁与单点故障的跨库 2PC 分布式事务。
- 所有审批决定本地入库 `ApprovalDB` 与 `wf_outbox` 处于单库本地事务，通过 `Approval.Worker` 异步回写 SAP Service Layer 并保证 At-least-once 投递 + 业务幂等。

### 2.4 快照与防篡改机制
- 提交审批时，系统拉取 SAP UDO 表头及全部子表生成规范化 JSON (Canonical JSON)，计算 SHA-256 哈希固化在 `wf_snapshot`。
- 审批通过回写前重新校验哈希，防止审批流转期间后台数据被私自篡改。

## 3. 后果与权衡 (Consequences)

### 积极影响 (Pros)
1. **彻底解耦**：审批平台独立演进，不侵入 SAP 核心表，也不依赖第三方平台源码。
2. **极高韧性**：SAP 维护重启或网络闪断期间，审批操作不丢失，待连接恢复后 Outbox 自动中继补偿。
3. **完整审计链**：快照与操作日志物理不可变，满足企业内控与审计合规要求。

### 负面影响与应对 (Trade-offs & Mitigations)
1. **SAP 状态最终一致性**：审批通过后 SAP 界面状态有秒级异步延迟。
   - *应对*：在 SAP 窗口提供“刷新”按钮与状态提示，引导用户主动拉取最新镜像状态。
